# Developer actions are a command surface, not connector capabilities

**Status**: accepted

Developer actions are internal commands owned by the developer-tool/API surface, not entries in the connector capability vocabulary. The toolbar and API know the explicit commands ahead of time; the API resolves the organization's enabled, configured integration by connector type through the existing connector registry and reuses the connector host/auth machinery, while each connector keeps a private dispatch map and validates its own action payloads. The API request keeps routing and operation separate — `{ organizationId, connectorType, action, payload }` — and intentionally omits an `integrationId` because the current domain permits one integration per connector type per organization. For entity-targeted commands, the browser sends the organization-scoped mirror row ID; the API authorizes and resolves it before forwarding a provider-neutral entity reference to the connector. Developer actions use a sibling `/api/actions/invoke` transport with the same shared-secret authentication and timeout conventions as capability invocation; `/api/capabilities/invoke` remains reserved for product capabilities. Developer actions use the existing Command K command-palette registry as their default UI; the toolbar may provide a compact entry point but is not a second action-definition system. All existing Devtools commands and controls migrate onto that shared registry so Command K is the single source of truth, but shared user-facing procedures such as `thread.create` are not changed or reclassified as internal in this project. Only commands backed by dev-exclusive API paths are eligible for the production internal-user gate; shared-procedure commands migrate locally but remain out of the production Devtools surface until future hardening. Local development preserves broad authenticated workspace access for practical testing; production-like deployments require the verified internal-domain predicate plus organization membership. Invocation is fire-and-forget after connector acceptance: the API returns a lightweight accepted/queued result, and structured logs carry actor, organization, action, target, and queue identifiers; no durable developer-action history is introduced in v1. External-entity replay refreshes the target first, re-checks authoritative eligibility, refuses an ineligible PR, and relies on the existing per-PR queue coalescing for repeated runs. GitHub backfill uses a multi-select repository picker with an explicit all-repositories option, then enqueues one idempotent job per selected repository. The production toolbar preserves existing diagnostics and developer controls for internal users; the security boundary is a server-side predicate requiring an authenticated, email-verified user with an exact case-insensitive `@tryfrontdesk.app` address plus membership in the target organization, with no secret exposure or cross-organization access. We do not add developer actions to manifests or expose runtime discovery, so product capability discovery remains limited to customer-facing connector roles and internal maintenance commands do not become public integration affordances.
