# Exchange long-lived API keys for one-time WebSocket tokens

Private and internal API keys authenticate ordinary HTTP requests through headers, but must never be placed in WebSocket URLs. A WebSocket client instead presents its long-lived key in a header to an exchange endpoint and receives an opaque, hashed-at-rest, 60-second token that is atomically consumed when opening one connection. The server-side, non-synced token record preserves the credential kind and authorization boundary: private-key tokens identify one organization and key, while internal-key tokens retain their distinct global trusted principal. This indirection prevents durable secrets from entering URLs while allowing both credential kinds to use the same connection machinery without granting private keys internal privileges.
